# Repository guidance

This repo is derived from a template located in https://github.com/microsoftgbb/iq-template. It owns its infrastructure, state, tests and CI/CD. Do not add compatibility code for older deployments.

## Start here

- [Getting started](docs/getting-started.md) is the canonical deployment guide; [developer setup](docs/development.md) covers Codespaces and Copilot App/CLI.
- `infra/` owns infrastructure, permissions and knowledge registration. Use plain Terraform and one ignored local tfvars file.
- `workspace/` owns Fabric definitions and bootstrap notebooks, not infrastructure, credentials or data backups.
- `agents/scenario-with-iq/` and `agents/scenario-without-iq/` own the two variants of one Foundry prompt agent: byte-identical `agent.json` and `instructions.md`, with only `tools/` differing ([agents](agents/README.md)). `app/` owns the Node.js/TypeScript web app on Azure Container Apps: the React page in `app/src/`, its agent layer in `app/src/live/` and its server in `app/server/` ([app](app/README.md)). The runner publishes the agents and builds the app's image; Terraform owns the registry, Container Apps environment, container app, identities, sign-in registrations and connections.
- Agents reply in Markdown with a source marker after each fact (`[D1]`, `[F1]` or `[F1 §2]`, `[Web1]`, `[W1]`), then *Sources* and *Steps* ([reply format](docs/architecture.md#reply-format)). Change the shared instructions, the app's parser (`app/src/live/reply.ts`) and the mock answers (`app/src/mock/client.ts`) together.
- [Official Copilot tooling](docs/copilot-tooling.md) covers the pinned Azure/Foundry IQ, Work IQ/M365 Agents Toolkit and Fabric packages. Product skills supplement this repository's ownership and approval rules; authoring MCP servers are not runtime agent/app connections.
- [Scenario authoring](docs/scenario-authoring.md) fixes domain, knowledge, agent, app and evaluation locations and the complete native work-package inventory. Do not improvise a competing project layout or backend.
- [`cicd/`](cicd/README.md) owns native Git/bootstrap/promotion guidance. [Ontology knowledge](docs/ontology-knowledge.md) explains binding and delegated retrieval.

## Always-on guardrails

- Everything in the sample is fictional: its sites, assets, documents and mail. Never write a real customer, company or person name into the repository.
- Never run live `plan`, `apply`, `destroy`, notebook execution or deployment tests as a template-maintenance check. Live work requires a derived repository and an explicitly chosen target.
- Route "deploy the platform" to the complete DEV workflow, not just infrastructure, through the [deterministic runner](docs/development.md#deploy-deterministically). Use one confirmed execution host/checkout/backend throughout; do not create duplicate state in an App worktree. Its `signin` phase completes every CLI sign-in, including the Microsoft Foundry token the agent phase uses, before anything is created; `--through verify` defers the agents and app. Require plan and action approvals and distinguish deployed resources from verified readiness.
- Do not delete cloud assets, local state or ignored configuration without explicit permission. Preserve unrelated user changes and staging.
- Never commit or print credentials, real tfvars, `.env`, state, saved plans or debug logs. Keep PATs ephemeral/write-only; rotate with `github_token_version`. Provider-returned secrets can remain in state: require secured remote state before team/CI use.
- Use `project_name` for resource branding; require an explicit region. Discover subscription/authentication through provider-supported CLI/environment conventions. Never bake a repository owner, tenant, subscription or physical Fabric ID into shared definitions.
- Preserve `.platform` logical IDs, TMDL lineage tags and binding markers: these are portable model identities, **not** deployment IDs. Resolve physical bindings in the current Fabric workspace. Keep the template ontology unbound; review generated DEV bindings only in derived repositories.
- Keep setup staged in one state: up-front CLI sign-in -> Entra bootstrap -> tenant-wide consent and the scoped sign-in -> Terraform platform -> native item import with an explicitly attached plan -> Terraform knowledge using physical DEV item GUIDs. Fabric Git sync is opt-in (`fabric_git_enabled = true`); only that path requires a PAT. The Foundry agents follow DEV readiness and live outside Terraform state, as project objects the runner publishes from the reviewed definitions; the container app, created once `app_image_tag` is set, is Terraform's, and the runner builds its image from committed files with ACR Tasks. Only the initial identity plan may target `module.fabric_user_auth`; all later platform/knowledge/destroy plans are untargeted. Preserve Fabric's identity-module dependencies so its login registration survives until Fabric teardown finishes.
- Declare delegated permissions and authorized clients. The deployer is assumed to administer every target: the runner grants tenant-wide consent for exactly the declared scopes and registers the subscription features the configuration needs as that user. Only when an API refuses for lack of permission does it stop with the exact grant an administrator must give; `--manual-grants` never attempts them. Never widen scopes or roles, self-assign directory privileges or change tenant settings to get past a refusal. Do not create credentials or grant directory-management permissions to the deployment app. No Terraform Git/seeding provisioners. The deterministic runner (`.github/skills/deploy-platform/scripts/deploy.py`) is recommended deployment automation, not mandatory. Prefer extending it rather than adding another wrapper. Alternative deployment paths must preserve explicit target selection, approvals, credential handling and readiness checks. TEST starts empty; tenant settings and PROD/approval gates are not template-owned.
- Preserve insert-only seeding, schema checks, current-workspace scope and explicit opt-in outside DEV/TEST. Preserve binding identity checks, unrelated definition parts, bounded polling and failure propagation. Serialize authoring/deployment; rebind every promoted target.
- Keep Search knowledge objects in data-plane `restful_resource` resources, with CRUD/drift detection and source rebuild/deletion ordering. Leave the source/base/MCP connection disabled when `knowledge_lakehouse_id` is null.
- Use native `fabricOntology` sources for live ontology queries. They require an end-user Search-audience token in `x-ms-query-source-authorization`; managed identities do not replace it. OneLake indexing's Search identity needs Contributor on DEV only, not a read-only lakehouse grant or access to TEST/PROD.
- Surface failures and documented preview/cost/public-networking limitations. A successful seed, deployment or registration is not proof of indexing, binding, graph or query readiness.
- The app calls only the two Foundry agents its settings name, through the Responses API of the one configured project, with each signed-in user's own token for `https://ai.azure.com/user_impersonation`. Its server verifies that token (issuer, audience, tenant, client, scope and object ID) before forwarding it, holds no secret and never calls Foundry with its own identity; its managed identity only pulls the image and publishes value-free traces to Application Insights, which accepts no ingestion key. Foundry's trace content stays in the protected `AppGenAIContent` table: never grant its reader role beyond the deployer.
- Fabric IQ runs as the signed-in user (a `UserEntraToken` connection; each user consents once). Work IQ is opt-in (`work_iq_enabled`) and runs as the signed-in user too, through the `work-iq` connection's OAuth identity passthrough; its registration is a public client without a secret, and the app sends no Work IQ token. The agents read the Foundry IQ and Web IQ knowledge bases as the project's managed identity, and Web IQ queries hold only public terms. Keep every MCP tool to its reviewed `allowed_tools` with `require_approval: never`, read-only. Never widen a role, scope, connection or tool list, or add a credential, to pass a check. Never commit a rendered agent definition, app settings or any file with physical IDs, tokens or deployment receipts.
- Prove the route with each user's own authorization and isolation ([runtime integration](docs/runtime-integration.md#evidence-required-for-a-ready-shell)). A published agent, a healthy container, an allowed connection or the current Fabric/knowledge DEV-ready report is not application-shell readiness, and a single-account run shows no isolation. Granting other users access is an operator step, not a template default. Never silently add a backend, change tenant policy, publish private Codespaces ports or relax the server's token checks to bypass a blocked integration; see [runtime troubleshooting](docs/runtime-integration.md#troubleshooting).

## Conventions and learning

Use snake_case Terraform labels, typed/documented inputs and outputs, explicit API versions and configurable model versions/SKUs/quota. Prefer native resources, keep `.terraform.lock.hcl`, and limit drift exclusions to documented service behavior.

Keep reusable learning at the narrowest useful scope: cross-task safety rules here, repeatable procedures in the matching skill, and product explanations in canonical docs. Correct the existing source instead of appending a session diary or duplicating instructions. Do not persist deployment IDs, credentials, personal details or unverified assumptions as guidance.

Keep README, getting started and the sanitized tfvars example aligned. Static Terraform checks are `init -backend=false`, `fmt -check -recursive`, and `validate`; use an isolated configuration copy when local deployment files exist. The maintenance skill explains safe checks for tooling and notebooks. Do not bundle project-specific deployment tests.
